[NOTE.antes]

Esta é a API de viagens que já rodava. Vamos chamá-la sem credencial nenhuma.

== Passo 1 -- chame a API sem credencial nenhuma

O comando pede só os cabeçalhos da resposta, que é onde a borda explica o que
decidiu.

[source,bash,role="execute perfil-qualquer",subs="attributes+"]
----
curl -s -o /dev/null -D - https://{api_host}/travels | grep -iE '^HTTP|www-authenticate|x-ext-auth-reason'
----

[source,text]
----
HTTP/2 401
www-authenticate: APIKEY realm="api-key-authn"
x-ext-auth-reason: credential not found
----

**O que isso diz:** a recusa veio com o motivo, e o motivo está no cabeçalho,
não no corpo. `credential not found` é a borda dizendo que nem chegou a
conferir nada: não havia o que conferir. O `realm` do `www-authenticate` é o
nome da regra de identidade que recusou.

== Passo 2 -- agora com uma chave que não existe

[source,bash,role="execute perfil-qualquer",subs="attributes+"]
----
curl -s -o /dev/null -D - -H 'Authorization: APIKEY nao-existe' "https://{api_host}/travels" | grep -iE '^HTTP|www-authenticate|x-ext-auth-reason'
----

[source,text]
----
HTTP/2 401
www-authenticate: APIKEY realm="api-key-authn"
x-ext-auth-reason: the API Key provided is invalid
----

**O que isso diz:** o código é o mesmo `401`, e o motivo mudou. Quem atende
um chamado de "não consigo acessar" começa por essa linha: ela separa quem
esqueceu a chave de quem tem a chave errada.

== Passo 3 -- e com uma chave que vale

A chave abaixo é a sua chave de teste do plano gold, a mesma da página
xref:acessos.adoc[Seus acessos].

[source,bash,role="execute perfil-qualquer",subs="attributes+"]
----
curl -s -o /dev/null -w '%{http_code}\n' -H 'Authorization: APIKEY {api_key_gold}' "https://{api_host}/travels"
----

[source,text]
----
200
----

**O que isso diz:** mesmo endereço, mesma aplicação, e a única diferença entre
o `401` e o `200` é a credencial. Nenhuma linha do `travels` trata disso.

NOTE: A chave viaja no header `Authorization: APIKEY <chave>`, não na URL. É
por isso que ela não aparece no access log do Gateway nem na URL de cada
trace: o que esses dois registram é o endereço, e o endereço não a carrega.

== Passo 4 -- a chave certa, na API errada

No mesmo ambiente há uma segunda API, a `echo-api`. Mande a ela a chave que
acabou de funcionar:

[source,bash,role="execute perfil-qualquer",subs="attributes+"]
----
curl -s -o /dev/null -w '%{http_code}\n' -H 'Authorization: APIKEY {api_key_gold}' "https://echo-travels.{cluster_domain}/"
----

[source,text]
----
302
----

**O que isso diz:** a chave não foi recusada, foi **ignorada**. A `echo-api`
não aceita chave de API: ela manda quem chega fazer login. Duas APIs, o mesmo
tipo de Gateway, credenciais diferentes -- a fronteira é por **API**, não "tem
chave ou não tem". A parte xref:m1-07-identidade.adoc[{p-identidade}] volta a
ela.

== Navegador: os dois lados da mesma porta

Abra o {portal_gold_url}[portal Vermelho^] e clique em **Buscar destinos**.
Funciona: 45 destinos.

Agora abra o mesmo endereço da API **direto no navegador**:

https://{api_host}/travels[https://{api_host}/travels^]

Tela em branco. É o mesmo serviço, no mesmo endereço, respondendo de formas
diferentes para dois clientes -- e a única diferença entre eles é a
credencial.

[TIP]
====
Abra as ferramentas de desenvolvedor **antes** de recarregar, na aba *Rede*. A
recusa vem com `401` e **zero bytes de corpo**: o motivo está no cabeçalho
`x-ext-auth-reason`, não na página. É por isso que a tela fica em branco em vez
de mostrar um erro.
====

O portal funciona porque o servidor dele acrescenta a chave a cada chamada.
Você, no navegador, não tem chave nenhuma.

O resultado é `destination_workload=unknown`: o destino é desconhecido

nunca foi acordada.

.Mais detalhes: o que a consulta faz, de dentro para fora
[%collapsible]
====
* `istio_requests_total{response_code="401"}` é o contador de requisições que
  o proxy do Gateway exporta, filtrado nas que terminaram em `401`. É
  acumulado desde que o pod subiu; sozinho, não diz nada sobre "agora".
* `increase(...[15m])` é quanto esse contador cresceu nos últimos 15 minutos:
  transforma o acumulado em "quantos 401 houve na última aula". O painel põe
  um `round()` por fora, porque o `increase` extrapola e pode devolver fração.
* `sum by (response_code, destination_workload)` soma todas as séries e guarda
  só dois rótulos: o código e o destino. Sem ele, apareceria uma linha por
  pod, por rota e por origem.

O rótulo que importa é `destination_workload`. Numa chamada que chegou à
aplicação ele vale o nome do deployment, `travels-v1`; no `401` ele sai
`unknown`, e é essa a prova: o Gateway recusou antes de encaminhar.
====

.Outro caso de uso: a mesma consulta na console do OpenShift

== Configuração

A `AuthPolicy` `travel-agency-authpolicy` é a policy que recusa. São vinte
linhas, e não há código de aplicação nenhum ali:

[source,bash,role="execute"]
----
oc get authpolicy travel-agency-authpolicy -n travel-agency -o yaml | head -40
----

O par dela é a `prod-web-deny-all`, o teto do gateway que ela sobrepõe:

[source,bash,role="execute"]
----
oc get authpolicy prod-web-deny-all -n ingress-gateway -o yaml
----

Não é um link para documentação: é a configuração que está no ar, lida do
cluster.

.Mais detalhes: o que cada campo da AuthPolicy faz
[%collapsible]
====
A policy que você abriu tem quatro decisões dentro, e vale saber o que cada
uma significa:

[source,yaml]
----
spec:
  targetRef:                    # <1>
    kind: HTTPRoute
    name: travel-agency
  rules:
    authentication:
      api-key-authn:
        apiKey:
          allNamespaces: false  # <2>
          selector:
            matchLabels:
              app: partner      # <3>
        credentials:
          authorizationHeader:
            prefix: APIKEY      # <4>
----

<1> **O alvo decide o alcance.** `kind: HTTPRoute` faz a policy valer só para
    esta rota. Se fosse `kind: Gateway`, valeria para todas as rotas anexadas
    -- é assim que o `prod-web-deny-all` funciona.
<2> **`allNamespaces: false`** limita a busca de chaves ao namespace da
    policy. Em `true`, o Authorino procura no cluster inteiro -- útil quando
    as chaves são administradas por um time central, arriscado quando não.
<3> **O seletor é o contrato.** Qualquer `Secret` com `app: partner` vira uma
    credencial válida. Criar um cliente novo é criar um Secret com esse label;
    revogar é apagá-lo. Não há banco de dados de chaves para sincronizar.

Num ambiente de turma o comando acima mostra **`allNamespaces: true`** nas
regras de identidade, e a `api-key-authn` traz um segundo rótulo no seletor,
`devportal.kuadrant.io/apiproduct: travels-api`: as suas chaves moram no
namespace da sua aplicação, e não no do Authorino. O `true` é seguro por causa
do seletor -- só vira credencial o `Secret` que tem os rótulos pedidos, e uma
regra de admissão do cluster impede que o rótulo de um participante sirva a
outro.
<4> **Onde a credencial viaja.** `authorizationHeader` é a forma usada aqui:
    o cliente manda `Authorization: APIKEY <chave>`, e a chave fica fora do
    access log e da URL do trace. O mesmo bloco aceita `customHeader` (um
    header próprio, como `X-API-Key`) e `queryString` (a chave na URL, que
    entra em log de acesso e em trace). Trocar o lugar da credencial é trocar
    este bloco; o resto da policy não muda. A parte xref:m1-06-exposta.adoc[{p-exposta}]
    mostra como aceitar dois formatos ao mesmo tempo, durante uma migração.
====

.Outro caso de uso: e se a autenticação for JWT/OIDC?
[%collapsible]
====
É a pergunta que mais aparece, e a resposta é que **muda o bloco, não a
arquitetura**. No lugar de `apiKey`, um `jwt`:

[source,yaml]
----
rules:
  authentication:
    meu-idp:
      jwt:
        issuerUrl: https://sso.exemplo.com/realms/clientes
----

O Authorino busca as chaves públicas do emissor, valida assinatura e
expiração, e o restante do roteiro continua idêntico -- inclusive o
`PlanPolicy`, que passa a ler o plano de uma *claim* do token em vez do label
do Secret.

Os dois convivem na mesma policy: uma rota pode aceitar chave de API para
parceiros antigos e JWT para os novos, com o mesmo alvo.
====

== O que isso prova

Nenhuma linha da aplicação trata autenticação -- o binário do `travels` é o
mesmo de antes de existir policy. Quem recusou foi o gateway, e a regra vale
para qualquer rota anexada a ele. É essa a diferença entre uma plataforma de
API e uma biblioteca de autenticação dentro de cada serviço.
