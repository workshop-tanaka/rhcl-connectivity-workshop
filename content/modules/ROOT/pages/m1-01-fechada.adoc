:navtitle: 1.1 Fechada por padrão

**Persona:** Segurança e Engenheiro de Plataforma -- e o Desenvolvedor, que não escreveu uma linha disto. · **2 min**

[NOTE.antes]
====
**Antes:** nada. Roda sozinho, a qualquer hora.

Esta é a API de viagens que já rodava. Vamos chamá-la sem credencial nenhuma.

== Terminal

[source,bash,role="execute"]
----
bash scripts/demo.sh ato1
----

O que tem de aparecer: `401` nas duas chamadas -- sem chave e com chave
inválida -- e o motivo no **cabeçalho**, não no corpo:
`x-ext-auth-reason: credential not found`.

== Navegador

Abra https://{api_host}/travels[https://{api_host}/travels^] com a aba *Rede* das ferramentas de
desenvolvedor aberta **antes**. A tela fica em branco: a recusa vem com zero
bytes de corpo. O ponto desta parte é que o motivo está no cabeçalho.

O contraste: https://{api_host}/travels?APIKEY={api_key_gold}[com a chave gold^] responde
`200` com JSON.

== Evidência

Painel **A.1 · 401 na borda: quem foi o destino?** em {grafana_url}/d/rhcl-evidencia[Evidência das partes^].

[source,promql]
----
sum by (response_code, destination_workload) (increase(istio_requests_total{response_code="401"}[15m]))
----

O resultado é `destination_workload=unknown`: o destino é desconhecido
**porque não houve destino**. A recusa foi contada na borda e a aplicação
nunca foi acordada.

== Configuração

{config_url}/base/policies-security/travel-agency-authpolicy.yaml[travel-agency-authpolicy.yaml^]
-- a policy que recusa. São vinte linhas, e não há código de aplicação nenhum
ali. O par é
{config_url}/base/policies-security/prod-web-deny-all.yaml[prod-web-deny-all.yaml^]:
o teto do gateway que ela sobrepõe.

Os dois arquivos vivem no GitLab **deste cluster**, com histórico e autoria --
não é um link para documentação, é a configuração que está no ar.

[source,bash,role="execute"]
----
oc get authpolicy travel-agency-authpolicy -n travel-agency -o yaml | head -40
----

.Mais detalhes: o que cada campo da AuthPolicy faz
[%collapsible]
====
A policy que você abriu tem quatro decisões dentro, e vale saber o que cada
uma significa:

[source,yaml]
----
spec:
  targetRef:                    # <1>
    kind: HTTPRoute
    name: travel-agency
  rules:
    authentication:
      api-key-authn:
        apiKey:
          allNamespaces: false  # <2>
          selector:
            matchLabels:
              app: partner      # <3>
        credentials:
          queryString:
            name: APIKEY        # <4>
----

<1> **O alvo decide o alcance.** `kind: HTTPRoute` faz a policy valer só para
    esta rota. Se fosse `kind: Gateway`, valeria para todas as rotas anexadas
    -- é assim que o `prod-web-deny-all` funciona.
<2> **`allNamespaces: false`** limita a busca de chaves ao namespace da
    policy. Em `true`, o Authorino procura no cluster inteiro -- útil quando
    as chaves são administradas por um time central, arriscado quando não.
<3> **O seletor é o contrato.** Qualquer `Secret` com `app: partner` vira uma
    credencial válida. Criar um cliente novo é criar um Secret com esse label;
    revogar é apagá-lo. Não há banco de dados de chaves para sincronizar.
<4> **Onde a credencial viaja.** `queryString` é o mais fácil de demonstrar,
    mas o mesmo bloco aceita `authorizationHeader` (o `Authorization: APIKEY
    <chave>`) e `customHeader`. Em produção, cabeçalho -- query string entra em
    log de acesso.
====

.Outro caso de uso: e se a autenticação for JWT/OIDC?
[%collapsible]
====
É a pergunta que mais aparece, e a resposta é que **muda o bloco, não a
arquitetura**. No lugar de `apiKey`, um `jwt`:

[source,yaml]
----
rules:
  authentication:
    meu-idp:
      jwt:
        issuerUrl: https://sso.exemplo.com/realms/clientes
----

O Authorino busca as chaves públicas do emissor, valida assinatura e
expiração, e o restante do roteiro continua idêntico -- inclusive o
`PlanPolicy`, que passa a ler o plano de uma *claim* do token em vez do label
do Secret.

Os dois convivem na mesma policy: uma rota pode aceitar chave de API para
parceiros antigos e JWT para os novos, com o mesmo alvo.
====

== O que isso prova

Nenhuma linha da aplicação trata autenticação -- o binário do `travels` é o
mesmo de antes de existir policy. Quem recusou foi o gateway, e a regra vale
para qualquer rota anexada a ele. É essa a diferença entre uma plataforma de
API e uma biblioteca de autenticação dentro de cada serviço.
