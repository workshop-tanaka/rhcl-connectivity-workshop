[NOTE.antes]
====
**Antes:** a parte xref:esteira-mr.adoc[{p-mr}Mudança por merge request], que mostra o caminho de um
merge request até o cluster.
====

A plataforma tem uma regra desde a parte
xref:m1-06-exposta.adoc[{p-exposta}]: **rota nova nasce com policy própria.**
Até aqui ela era um conselho -- uma rota sem `AuthPolicy` fica aberta até o
teto do Gateway alcançá-la, e isso já foi medido neste workshop. Nesta parte a
regra vira **portão**: o merge request que a fere não entra no `main`.

Quem confere é o **OpenShift Pipelines**. A cada push num merge request, o
Pipelines as Code recebe o aviso do GitLab, roda um `PipelineRun` no namespace
`esteira-ci-{user}` e devolve o resultado ao merge request. A definição do
pipeline é lida do `main`, e o script da regra é uma cópia da plataforma: quem
abre o merge request não escolhe o pipeline nem a regra que o conferem.

== Passo 1 -- uma rota nova, sem policy

A equipe precisa publicar `/relatorios` na API de viagens. O comando cria a
rota na pasta da esteira e roda a mesma conferência do CI, no seu terminal.

[source,bash,role="execute perfil-dev",subs="attributes+"]
----
git checkout -q main && git pull -q
git checkout -q -B rota-relatorios
cat > esteira/relatorios.yaml <<'EOF'
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: {name: relatorios}
spec:
  parentRefs: [{name: prod-web, namespace: ingress-gateway}]
  hostnames: ["{api_host}"]
  rules: [{matches: [{path: {type: PathPrefix, value: /relatorios}}], backendRefs: [{name: travels, port: 8000}]}]
EOF
echo '  - relatorios.yaml' >> esteira/kustomization.yaml
bash scripts/esteira.sh confere
----

[source,text]
----
    ok  PlanPolicy/travels-plans                 tipo aceito pela esteira
    ok  PlanPolicy/travels-plans                 no namespace travel-agency-...
    ok  HTTPRoute/relatorios                     tipo aceito pela esteira
    ok  HTTPRoute/relatorios                     no namespace travel-agency-...
    NAO HTTPRoute/relatorios                     tem AuthPolicy propria na pasta
    ok  HTTPRoute/relatorios                     presa a um Gateway deste ambiente

    RECUSADO: 1 regra(s) nao atendida(s) -- corrija antes do merge request
----

[WARNING]
.Recusa esperada -- a conferência barra a rota sem policy
====
`RECUSADO` é o resultado deste passo: a rota não tem `AuthPolicy` própria.
====

**O que isso diz:** das quatro regras, só a terceira falhou. As outras três o
cluster também recusaria; esta, não -- uma rota sem policy é aceita pelo
cluster e fica aberta. É por isso que ela precisa de um portão antes.

== Passo 2 -- abra o merge request mesmo assim

Suponha que você não rodou a conferência, ou ignorou o resultado. O comando
abre o merge request e, meio minuto depois, lê o que o OpenShift Pipelines
decidiu.

[source,bash,role="execute perfil-dev",subs="attributes+"]
----
git add esteira && git commit -q -m 'relatorios: rota nova'
git push -f -o merge_request.create -o merge_request.title='rota de relatorios' origin rota-relatorios 2>&1 | grep -E 'merge_requests|new branch'
sleep 30
tkn pipelinerun list -n esteira-ci-{user} --limit 1
tkn pipelinerun logs --last -n esteira-ci-{user} 2>&1 | grep -E 'NAO|RECUSADO'
----

[source,text]
----
remote:   https://.../workshop/participantes/.../ambiente/-/merge_requests/N
 * [new branch]      rota-relatorios -> rota-relatorios
NAME            STARTED          DURATION   STATUS
confere-...     25 seconds ago   8s         Failed
[confere : confere]     NAO HTTPRoute/relatorios                     tem AuthPolicy propria na pasta
[confere : confere]     RECUSADO: 1 regra(s) nao atendida(s) -- corrija antes do merge request
----

Abra o endereço do merge request. O status **Pipelines as Code CI /
confere** está vermelho e o merge, bloqueado.

**Na console web:** o mesmo `PipelineRun`, na console do OpenShift -- os
PipelineRuns de {openshift_console_url}/k8s/ns/esteira-ci-{user}/tekton.dev{tilde}v1{tilde}PipelineRun[`esteira-ci-{user}`^]
(abre em aba nova), com o login Infra ou Dev: os dois leem, nenhum muda.

.Navegando, passo a passo
[%collapsible]
====
. Abra o link e entre com o seu login da console, Infra ou Dev.
. A lista traz um `confere-...` por push num merge request, com *Succeeded*
  ou *Failed* -- o do passo 2 aparece como falho, como no
  `tkn pipelinerun list`.
. Clique nele: a aba *Logs* mostra a mesma recusa do
  `tkn pipelinerun logs` (`NAO HTTPRoute/relatorios ...`), e a aba
  *TaskRuns*, a tarefa `confere`.
. Em *Actions*, *Rerun* e *Delete PipelineRun* vêm desabilitados, com
  *Insufficient permissions*: quem roda a conferência é o webhook do GitLab,
  não você.
. Sem o link: no menu *Pipelines* da console, com o projeto
  `esteira-ci-{user}` escolhido no alto.
====

[WARNING]
.Recusa esperada -- o merge request não entra sem a conferência verde
====
O status vermelho e o merge bloqueado são o resultado -- **nem o perfil Infra**
consegue aceitar este merge request: o projeto só aceita merge com a
conferência verde.
====

**O que isso diz:** a aprovação humana não substitui a conferência. Quem
aprova lê a mudança; a máquina garante as regras que ninguém deve precisar
lembrar.

== Passo 3 -- conserte no mesmo merge request

A rota passa a nascer com chave: uma `AuthPolicy` cujo alvo é ela.

[source,bash,role="execute perfil-dev"]
----
cat > esteira/relatorios-chave.yaml <<'EOF'
apiVersion: kuadrant.io/v1
kind: AuthPolicy
metadata: {name: relatorios-chave}
spec:
  targetRef: {group: gateway.networking.k8s.io, kind: HTTPRoute, name: relatorios}
  rules:
    authentication:
      chave:
        apiKey: {allNamespaces: true, selector: {matchLabels: {app: partner}}}
        credentials: {authorizationHeader: {prefix: APIKEY}}
EOF
echo '  - relatorios-chave.yaml' >> esteira/kustomization.yaml
bash scripts/esteira.sh confere | tail -1
git add esteira && git commit -q -m 'relatorios: a rota nasce com chave'
git push origin rota-relatorios 2>&1 | grep -E 'rota-relatorios'
----

[source,text]
----
    CONFERIDO: pode abrir o merge request
   ...  rota-relatorios -> rota-relatorios
----

O push atualiza o **mesmo** merge request, e uma conferência nova roda sobre
ele.

[IMPORTANT]
.Perfil Infra -- no GitLab, como `{usuario_console}`
====
Quem aceita é o **perfil Infra**. No navegador você já está no GitLab como
`{usuario_console}` (o login do console), que é *Maintainer* do projeto. Abra
o endereço do merge request: na aba **Changes** está a rota **e** a policy dela; espere a conferência
**Pipelines as Code CI / confere** ficar verde e clique em **Merge**.
====

**O que isso diz:** a conferência ficou verde porque a mudança passou a
cumprir a regra -- e só então o Infra pôde aceitar.

== Passo 4 -- espere a esteira, e chame a rota

[source,bash,role="execute perfil-dev",subs="attributes+"]
----
git checkout -q main && git pull -q
bash scripts/esteira.sh espera
bash scripts/esteira.sh estado | tail -3
curl -s -o /dev/null -w 'sem chave: %{http_code}\n' "https://{api_host}/relatorios"
curl -s -o /dev/null -w 'com chave: %{http_code}\n' -H 'Authorization: APIKEY {api_key_gold}' "https://{api_host}/relatorios"
----

[source,text]
----
    esperando o commit 385d9922 chegar ao cluster .............................
    aplicado em 227s  (cluster x Git: Synced)
      PlanPolicy/travels-plans  Synced
      HTTPRoute/relatorios  Synced
      AuthPolicy/relatorios-chave  Synced
sem chave: 401
com chave: 404
----

Os seus tempos vão ser outros: o GitLab avisa o Argo CD a cada push, e medi
de um segundo a quase quatro minutos neste ambiente.

**O que isso diz:** a rota e a policy chegaram ao cluster **no mesmo commit**
-- não houve um instante em que `/relatorios` respondesse sem chave. O `404`
com chave é da aplicação, que não tem esse caminho: a borda deixou passar,
que era o trabalho dela.

== Passo 5 -- tire a rota, pelo mesmo caminho

[source,bash,role="execute perfil-dev"]
----
git checkout -q -B tira-relatorios
git revert --no-edit -m 1 "$(git log --merges -1 --format=%H --grep=rota-relatorios)" | head -1
git push -f -o merge_request.create -o merge_request.title='tira a rota de relatorios' origin tira-relatorios 2>&1 | grep -E 'merge_requests'
----

[IMPORTANT]
.Perfil Infra -- no GitLab, como `{usuario_console}`
====
Quem aceita é o **perfil Infra**. No navegador você já está no GitLab como
`{usuario_console}` (o login do console), que é *Maintainer* do projeto. Abra
o endereço do merge request: na aba **Changes** está o revert: as duas saem; espere a conferência
**Pipelines as Code CI / confere** ficar verde e clique em **Merge**.
====

Depois do merge, de volta ao terminal Dev:

[source,bash,role="execute perfil-dev"]
----
git checkout -q main && git pull -q
bash scripts/esteira.sh espera
bash scripts/esteira.sh estado | tail -2
----

[source,text]
----
    esperando o commit 6fcfe2ac chegar ao cluster
    aplicado em 1s  (cluster x Git: Synced)
    cluster x Git          Synced
      PlanPolicy/travels-plans  Synced
----

**O que isso diz:** a rota e a policy saíram do cluster porque saíram do Git.
A esteira apaga o que deixou de estar na pasta -- e só o que ela mesma
aplicou.

== O que isso prova

**A regra da plataforma vira portão, não lembrete.** Rota sem policy não chega
ao `main`, e por isso não chega ao cluster. Quem escreve a regra é a
plataforma, uma vez, num lugar que as equipes leem e não mudam; quem a
encontra no caminho é cada merge request.

.Como isso foi montado
[%collapsible]
====
* o **OpenShift Pipelines**, com o **Pipelines as Code** que vem nele; o GitLab
  o avisa a cada push num merge request;
* um `Repository` do Pipelines as Code por participante, no namespace
  `esteira-ci-{user}`, que lê a definição do pipeline do `main`
  (`.tekton/confere.yaml`), nunca do branch do merge request;
* o pipeline recusa merge request que mexa fora de `esteira/` e roda
  `esteira.sh confere` a partir de uma cópia da plataforma;
* o seu projeto só aceita merge com a conferência verde; o perfil Dev é
  *Developer* nele: abre o merge request e não o aceita -- quem aceita é o
  Infra, *Maintainer* -- e nenhum dos dois muda essas configurações;
* no `esteira-ci-{user}` você **vê** as execuções e não muda nada.
====
