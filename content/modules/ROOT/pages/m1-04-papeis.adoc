= {p-papeis} Quem pode o quê
:navtitle: {p-papeis} Quem pode o quê

**Para quem:** Engenheiro de Plataforma e Desenvolvedor -- os dois papéis que o Gateway API nomeia. · **7 min**

[NOTE.antes]
====
**Antes:** nenhuma parte. Faz muito mais sentido logo depois da {p-precedencia}, que mostra a
precedência no status; aqui ela deixa de ser afirmação.
====

A especificação do Gateway API não define só recursos: define **papéis**. E o
Connectivity Link herda os três. Dois deles aparecem neste exercício:

[cols="1,2,3",options="header"]
|===
| Papel na especificação | Aqui | Governa

| Cluster Operator
| `plat-eng`
| o `Gateway` e as policies que miram o **gateway** -- o teto: `deny-all`,
  limite baixo, TLS, DNS

| Application Developer
| `app-dev`
| a `HTTPRoute` do próprio serviço e as policies que miram **essa rota** --
  autenticação, plano comercial, telemetria
|===

A parte {p-precedencia} mostrou a precedência num campo de status. Aqui quem responde é o
**apiserver**.

== Terminal

ifndef::foco_rhcl[]
[source,bash,role="execute"]
----
bash scripts/demo.sh papeis
----

O passo tem duas camadas. Vale entender a diferença entre elas.
endif::[]
ifdef::foco_rhcl[]
São duas camadas: a primeira **pergunta** ao cluster o que cada papel pode; a
segunda **age** como o desenvolvedor.
endif::[]

=== Camada 1: a matriz, perguntada ao cluster

[source,bash,role="execute"]
----
oc auth can-i patch authpolicy -n ingress-gateway --as=app-dev
oc auth can-i patch authpolicy -n ingress-gateway --as=plat-eng
----

`oc auth can-i --as=` pergunta ao apiserver o que **outra** pessoa poderia
fazer, sem virar ela. O resultado, lado a lado:

[cols="3,1,1",options="header"]
|===
| Ação | `app-dev` | `plat-eng`

| editar a AuthPolicy do **gateway** | no | yes
| editar a RateLimitPolicy do **gateway** | no | yes
| mudar o próprio `Gateway` | no | yes
| **ver** o `Gateway` a que se anexa | **yes** | yes
| criar a própria `HTTPRoute` | yes | yes
| criar a policy da **própria rota** | yes | yes
| ler segredos da plataforma | no | yes
|===

Repare na linha do meio, que é a que costuma passar despercebida: o
desenvolvedor **pode ver** o Gateway. Sem essa leitura ele não descobre o nome
para o `parentRefs`, e o modelo viraria "abra um ticket para a plataforma" --
exatamente o que o Gateway API existe para eliminar.

.E se fosse uma `Route` do OpenShift?
[%collapsible]
====
A matriz acima só existe porque a porta e a rota são **dois objetos**. Numa
`Route`, hostname, TLS e destino moram juntos, e quem tem permissão de editá-la
decide os três. Não há um objeto "gateway" onde o Engenheiro de Plataforma
escreva um teto -- e o `deny-all` da parte xref:m1-06-exposta.adoc[{p-exposta}] não
teria onde existir.

Neste cluster dá para ver a diferença na prática:

[source,bash,role="execute"]
----
oc auth can-i create routes -n travel-agency --as=app-dev
oc auth can-i create httproutes.gateway.networking.k8s.io -n travel-agency --as=app-dev
oc auth can-i create gateways.gateway.networking.k8s.io -n ingress-gateway --as=app-dev
----

`no`, `yes`, `no`: o desenvolvedor publica a própria rota **atrás** da porta da
plataforma, e não uma porta nova. A primeira resposta é uma decisão de RBAC
deste ambiente; as outras duas são o modelo que a
xref:leitura-ingresso.adoc[leitura sobre Route, Ingress e Gateway API] descreve.
====

=== Camada 2: você age como o desenvolvedor

Perguntar não é o mesmo que tentar. Os próximos comandos são executados **com
a identidade do desenvolvedor**, e a sua sessão não muda: a identidade vai em
cada comando, e não num login.

==== Tente mexer no teto da plataforma

O comando tenta pôr uma anotação na `prod-web-deny-all`, a policy que nega
tudo no Gateway.

[source,bash,role="execute"]
----
oc patch authpolicy prod-web-deny-all -n ingress-gateway --type=merge -p '{"metadata":{"annotations":{"teste":"1"}}}' --as=app-dev
----

[source,text]
----
Error from server (Forbidden): authpolicies.kuadrant.io "prod-web-deny-all" is forbidden:
User "..." cannot get resource "authpolicies" in API group "kuadrant.io" in the namespace "ingress-gateway"
----

**O que isso diz:** leia a mensagem inteira. Ela traz o **nome de quem
tentou**. Isso não é convenção de equipe, nem revisão de código, nem um
combinado que alguém pode furar com pressa: é o apiserver recusando.

==== E o que ele pode

Primeiro, **ver** o Gateway a que a rota dele se prende:

[source,bash,role="execute"]
----
oc get gateway prod-web -n ingress-gateway --as=app-dev
----

[source,text]
----
NAME       CLASS   ADDRESS                                            PROGRAMMED   AGE
prod-web   istio   prod-web-istio.ingress-gateway.svc.cluster.local   True         ...
----

Depois, **mudar** a policy comercial da rota dele. O comando põe uma anotação
na `PlanPolicy`, e o seguinte a tira:

[source,bash,role="execute"]
----
oc annotate planpolicy travels-plans -n travel-agency rhcl.demo/tocado-por=dev --overwrite --as=app-dev
oc annotate planpolicy travels-plans -n travel-agency rhcl.demo/tocado-por- --as=app-dev
----

[source,text]
----
planpolicy.extensions.kuadrant.io/travels-plans annotated
planpolicy.extensions.kuadrant.io/travels-plans annotated
----

**O que isso diz:** ele vê o Gateway e não o muda; muda a policy da rota dele
sem pedir a ninguém. E essa policy **prevalece** sobre a do Gateway -- foi o
que o status mostrou na parte xref:m1-03-precedencia.adoc[{p-precedencia}].
Precedência sem privilégio: o desenvolvedor governa o que é dele e não alcança
o que não é, e quem recusa é o cluster.

=== Camada 2: você age como o desenvolvedor

Perguntar não é o mesmo que tentar. Agora **troque de aba**: os próximos
comandos rodam no `Terminal Dev`, com a identidade do desenvolvedor do seu
ambiente -- uma conta diferente da sua, e não um disfarce.

==== Tente mexer no teto da plataforma

O comando tenta pôr uma anotação na `prod-web-deny-all`, a policy que nega
tudo no Gateway.

[source,bash,role="execute perfil-dev"]
----
oc patch authpolicy prod-web-deny-all -n ingress-gateway --type=merge -p '{"metadata":{"annotations":{"teste":"1"}}}' && oc annotate authpolicy prod-web-deny-all -n ingress-gateway teste-
----

[source,text]
----
Error from server (Forbidden): authpolicies.kuadrant.io "prod-web-deny-all" is forbidden:
User "system:serviceaccount:travel-agency-...:dev" cannot patch resource "authpolicies" in API group "kuadrant.io" in the namespace "ingress-gateway-..."
----

[WARNING]
.Erro esperado -- o perfil Dev não pode mexer no Gateway
====
A recusa é o resultado desta parte. Leia a mensagem inteira: ela traz o
**nome de quem tentou** (`...:dev`), o **verbo** (`patch`: ler ele pode, mudar
não), o **recurso** (`authpolicies`) e o **lugar** (o namespace do Gateway). Isso não é convenção de equipe, nem
revisão de código, nem um combinado que alguém pode furar com pressa: é o
apiserver recusando.

O mesmo comando, na aba `Terminal Infra`, passaria. Se você clicar nele
com essa aba aberta, o terminal avisa que o bloco é do Dev e pergunta se roda
mesmo assim: responda `s` para ver o Infra conseguir. A segunda metade da
linha (`&& oc annotate ... teste-`) tira a anotação logo em seguida, e o
Gateway fica como estava. Como Dev, a primeira metade é recusada e a segunda
nem roda.

==== O mesmo, na console

O perfil Dev tem também o seu login na console: `{usuario_console_dev}`.
Saia (**Log out**, no canto superior direito) e entre com ele -- a senha está em
xref:acessos.adoc[Seus acessos]. Depois abra o Gateway:

{openshift_console_url}/k8s/ns/ingress-gateway/gateway.networking.k8s.io{tilde}v1{tilde}Gateway/prod-web[o Gateway `prod-web`^]

Os detalhes e as policies dele aparecem, mas o editor de YAML abre **só para
leitura** -- a console já sabe que esta identidade não muda o Gateway. Mais
quatro telas, cada uma com o mesmo recado:

[cols="2,3",options="header"]
|===
| tela | o que o perfil Dev vê

| {openshift_console_url}/k8s/cluster/projects[Projects^]
| só os dois projetos dele: a aplicação e o Gateway

| {openshift_console_url}/kuadrant/policies/ns/ingress-gateway[Policies do Gateway^]
| as policies do Gateway, com status -- e o botão **Create Policy cinza**: ver
  ele pode, criar não

| {openshift_console_url}/kuadrant/policies/ns/travel-agency[Policies da aplicação^]
| as da rota dele, e ali o **Create Policy é azul**: este é o lugar dele

| {openshift_console_url}/kuadrant/policy-topology/ns/travel-agency[Policy Topology^]
| *Access Denied*, e a console diz o que falta: ler o `ConfigMap topology` de
  `kuadrant-system`, o mapa da plataforma inteira -- o mesmo que o seu perfil
  Infra recebe, como você verá logo abaixo
|===

É a mesma regra do terminal, aplicada à tela: uma pessoa, dois papéis, e o
cluster decide o que cada um vê -- e a tela explica a recusa em vez de
esconder o botão sem dizer por quê.

Para voltar ao perfil Infra, saia e entre de novo com `{usuario_console}`.
endif::[]

ifeval::["{usuario_console_plataforma}" != ""]
==== O terceiro login: a plataforma, só leitura

Os dois perfis recortam o cluster por **projeto**: cada um vê os projetos
dele, e o Infra vê mais que o Dev. Mas o Connectivity Link tem **um plano de
controle por cluster** -- um operator, um Authorino, um Limitador para todos os
Gateways --, e uma parte do que ele produz não mora no projeto de ninguém:

[cols="2,3",options="header"]
|===
| o quê | por que não cabe no seu projeto

| a Policy Topology
| ela desenha um único objeto, o `ConfigMap topology` de `kuadrant-system`. O
  RBAC concede um objeto inteiro ou nada: não existe "ler só as linhas do
  user5". O filtro por namespace teria de vir do próprio plugin da console, e
  ele não o tem

| o `Limitador` e os `AuthConfig` gerados
| o operator escreve em `kuadrant-system` o que derivou das policies de
  **todos** -- um contador por plano de cada participante, um `AuthConfig` por
  regra de cada rota

| a tela de alertas do cluster
| *Observe → Alerting* da administração mostra os alertas de todos os projetos
  e os da plataforma; a sua regra você já vê no seu projeto (parte {p-alerta})
|===

Três saídas foram consideradas, e a escolha diz algo sobre como desenhar
acesso em produção:

* **Dar isso ao seu perfil Infra.** Era o que esta turma fazia. Funciona, mas
  mistura "os meus projetos" com "o cluster de todos" -- o perfil deixa de
  dizer, sozinho, o que a pessoa governa.
* **O papel `cluster-reader` do OpenShift.** Ele não lê `Secret`, e parece
  bastar. Não basta: lê a spec de todo `Deployment`, `Pod` e `ConfigMap` do
  cluster, e credencial também mora ali. Neste cluster, medido antes de
  decidir, havia segredo escrito em variável de ambiente do registro de
  imagens e do Pipelines, e em `ConfigMap` do GitLab. "Só leitura" não é o
  mesmo que "sem segredo".
* **Um papel fechado, num login à parte.** É o escolhido:
  `rhcl-plataforma-leitura` lista o que se lê, um tipo de objeto por vez -- os
  objetos de Gateway API, de Connectivity Link e de Istio do cluster, e só
  `kuadrant-system` por dentro. Ficam de fora `Secret`, log de pod (a chave de
  API ainda viaja na URL), `exec`, `ConfigMap` (fora o `topology`) e qualquer
  verbo de escrita.

O login é `{usuario_console_plataforma}`, **o mesmo para a turma inteira** --
a visão é a mesma para todos, e a senha está em todos os guias. Isso só é
aceitável porque ele não escreve nada e não lê segredo. Em produção, no lugar
de um login compartilhado, o papel iria para o **grupo** do time de
plataforma no provedor de identidade.

Saia (*Log out*), entre como `{usuario_console_plataforma}` e abra:

[cols="2,3",options="header"]
|===
| tela | o que mostra

| {openshift_console_url}/kuadrant/policy-topology/all-namespaces[Policy Topology^]
| o mapa inteiro: os Gateways, as rotas e as policies da turma, e os
  `AuthConfig` que ninguém escreveu à mão

| {openshift_console_url}/k8s/ns/kuadrant-system/limitador.kuadrant.io{tilde}v1alpha1{tilde}Limitador/limitador/yaml[O Limitador^]
| em `spec.limits`, um limite por plano de **cada** participante -- o que a
  sua `PlanPolicy` virou, ao lado do que a dos colegas virou

| {openshift_console_url}/k8s/ns/kuadrant-system/authorino.kuadrant.io{tilde}v1beta3{tilde}AuthConfig[Os AuthConfig^]
| um por regra de cada rota, gerados pelo operator: é o que o Authorino
  executa

| {openshift_console_url}/k8s/ns/kuadrant-system/operators.coreos.com{tilde}v1alpha1{tilde}ClusterServiceVersion[Installed Operators^]
| o Connectivity Link instalado uma vez, para todos

| {openshift_console_url}/k8s/ns/kuadrant-system/secrets[Secrets^]
| *Restricted access* -- nem a plataforma, por esta tela, lê as chaves
|===

Tente editar qualquer um deles: o editor de YAML abre só para leitura.

Depois volte ao seu login, `{usuario_console}`.
endif::[]

== Evidência

[source,bash,role="execute"]
----
oc get gateway prod-web -n ingress-gateway -o jsonpath='{.spec.listeners[0].allowedRoutes.namespaces.from}{"\n"}'
----

A resposta é `All` ou `Selector`. **A delegação não é um combinado verbal:
está escrita no próprio Gateway.** Com `All`, quem cuida da plataforma declarou
que qualquer namespace pode anexar rota ao `prod-web`; com `Selector`, só os
namespaces que carregam um rótulo -- é o caso de um ambiente de turma, em que o
Gateway de cada participante aceita rota só dos namespaces dele. Nos dois, o
desenvolvedor publica sem pedir nada a ninguém.

== Configuração

[source,bash,role="execute"]
----
oc get role,rolebinding -n travel-agency | grep app-dev
oc describe role app-dev-dono-da-rota -n travel-agency
----

Um `Role` no namespace da aplicação e um `ClusterRole` de leitura só para
`gateways`. Nada além disso.

== O que isso prova

**Precedência sem privilégio.** O desenvolvedor governa o que é dele e não
alcança o que não é -- e a policy dele *prevalece* sobre a do gateway na rota
dele, que foi o que a parte {p-precedencia} mostrou no status.

Ninguém precisou escrever um processo, um checklist de revisão ou um acordo
entre times para isso funcionar. O cluster é quem recusa. É essa a diferença
entre uma plataforma de API e um gateway com um documento de boas práticas ao
lado.
