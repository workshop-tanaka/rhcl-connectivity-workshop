**Opcional · ~7 min · cria e remove um namespace próprio**
endif::[]
ifdef::foco_rhcl[]
**~8 min · cria e remove um projeto próprio**

**Para quem:** Engenheiro de Plataforma e Arquitetura -- quem opera a borda, e quem vai desenhar mais de um cluster.

[NOTE.antes]
====
**Antes:** a parte xref:m1-06-exposta.adoc[{p-exposta}], que publica uma API com
`HTTPRoute` num Gateway. Aqui entra a peça que falta: **o nome** pelo qual
alguém a encontra.
====

Das policies do xref:mapa-policies.adoc[mapa], a `DNSPolicy` é a que mais pede
do ambiente: a leitura óbvia da documentação pede conta em nuvem, domínio público e um endereço externo para
publicar.

Só que o operador de DNS deste ambiente registra **cinco provedores**, e dois
deles rodam dentro do cluster:

[source,text]
----
init provider factory  providers: ["coredns","endpoint","aws","azure","google"]
----

Com o provedor `coredns`, o exercício inteiro cabe num namespace.

== Terminal

ifndef::foco_rhcl[]
[source,bash,role="execute"]
----
bash scripts/dns-nome.sh
----

Leva cerca de dois minutos, e remove tudo no fim. O script sobe uma zona de
mentira (`dns-lab.rhcl.internal`) servida por um CoreDNS do próprio laboratório,
um Gateway próprio, e o cliente é um pod.
endif::[]
ifdef::foco_rhcl[]
A parte acontece num **projeto só dela**, `dns-lab`, com uma zona de mentira
(`dns-lab.rhcl.internal`) servida por um CoreDNS do próprio laboratório. Os três
arquivos estão em `passos/dns/`.

Monte o laboratório. O arquivo sobe o CoreDNS da zona, uma aplicação, um pod
cliente e o Gateway; os três comandos seguintes esperam cada peça ficar pronta.

[source,bash,role="execute"]
----
oc new-project dns-lab --skip-config-write
oc apply -f passos/dns/01-laboratorio.yaml
oc rollout status deploy/coredns -n dns-lab --timeout=180s
oc wait --for=condition=Programmed gateway/lab -n dns-lab --timeout=120s
oc wait --for=condition=Ready pod/cliente -n dns-lab --timeout=180s
----

[source,text]
----
deployment "coredns" successfully rolled out
gateway.gateway.networking.k8s.io/lab condition met
pod/cliente condition met
----

Abra o arquivo e repare no que **não** está nele: nenhum registro de DNS. O
Gateway declara que responde por `api.dns-lab.rhcl.internal`, e ninguém criou esse
nome.

.Se você é administrador do cluster, e não participante de uma turma
[%collapsible]
====
O CoreDNS do laboratório precisa ler os registros no cluster inteiro. Numa
turma essa permissão já vem pronta; fora dela, aplique antes:

[source,bash]
----
oc apply -f passos/dns/00-permissao-de-cluster.yaml
----
====
endif::[]

[IMPORTANT]
====
**Nada disto toca o DNS do cluster.** A zona não existe fora do laboratório, e
quem a serve é um CoreDNS que sobe e desce com o exercício. O `prod-web` e os
nomes do workshop seguem intocados.
====

== 1. O Gateway está pronto, e ninguém o encontra

ifdef::foco_rhcl[]
Pergunte o nome ao CoreDNS do laboratório. O terminal não tem `dig`, e a zona
só existe dentro do cluster: a consulta sai do pod cliente, por uma ferramenta
pequena.

[source,bash,role="execute"]
----
bash scripts/dns-nome.sh resolve
----

endif::[]
[source,text]
----
pergunta: api  (zona dns-lab.rhcl.internal, ao CoreDNS do laboratorio)
NXDOMAIN -- ninguem criou o nome "api" nesta zona
----

O terminal escreve a zona uma vez e os nomes curtos: `api` é
`api.dns-lab.rhcl.internal`.

O `Gateway` está `Programmed`, a `HTTPRoute` está anexada, o serviço responde.
Falta o nome -- e **isso é trabalho de outra equipe**, na maioria das empresas,
com outro chamado e outro prazo.

== 2. Uma policy, e os registros aparecem

ifdef::foco_rhcl[]
Aplique a policy, espere ela entrar em vigor, e leia o que apareceu. O `sleep`
dá ao operador os segundos que ele leva para criar os registros.

[source,bash,role="execute"]
----
oc apply -f passos/dns/02-dnspolicy.yaml
oc wait --for=condition=Enforced dnspolicy/lab -n dns-lab --timeout=90s
sleep 10
oc get dnspolicy lab -n dns-lab -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.message}{"\n"}{end}'
bash scripts/dns-nome.sh registros
----

O arquivo traz a policy abaixo e o `Secret` do provedor:

endif::[]
[source,yaml]
----
apiVersion: kuadrant.io/v1
kind: DNSPolicy
spec:
  targetRef: {group: gateway.networking.k8s.io, kind: Gateway, name: lab}
  providerRefs: [{name: coredns-provider}]
----

O `Secret` do provedor tem duas linhas: o tipo `kuadrant.io/coredns` e a zona.

[source,text]
----
Accepted=True   DNSPolicy has been accepted
Enforced=True   DNSPolicy has been successfully enforced

DNSRecord lab-http  Ready=True
  derivado pela DNSPolicy lab do listener "http" do Gateway
DNSRecord authoritative-record-...  Ready=True
  o que o CoreDNS serve (tem o label kuadrant.io/coredns-zone-name)

zona dns-lab.rhcl.internal
api
└─ CNAME lab-istio (svc)               o Gateway deste cluster
----

Você não escreveu registro nenhum. **O operador leu o listener do Gateway** e
derivou o nome, o tipo e o destino. São dois `DNSRecord`, e cada linha diz o
papel do seu: o `lab-http` é o que a policy derivou do listener `http` -- o
dono dele é a `DNSPolicy` --, e o `authoritative-record` é o que o servidor da
zona publica. A árvore embaixo é o conteúdo. É o mesmo padrão da parte
xref:m1-08-certificado.adoc[{p-certificado}] com a `TLSPolicy`, e da
xref:m1-07-identidade.adoc[{p-identidade}] com a `OIDCPolicy`: intenção declarada, objeto
derivado, com dono. O dono vai importar na seção 5, abaixo.

E repare em **como o CoreDNS descobre o registro**: pelo label
`kuadrant.io/coredns-zone-name` que o operador carimbou. Não há arquivo de zona
editado à mão, nem recarga de servidor.

== 3. O nome resolve, e responde

ifdef::foco_rhcl[]
A mesma pergunta de antes, agora com resposta:

[source,bash,role="execute"]
----
bash scripts/dns-nome.sh resolve
----

endif::[]
[source,text]
----
pergunta: api  (zona dns-lab.rhcl.internal, ao CoreDNS do laboratorio)
api        CNAME  lab-istio (svc)       o nome publico -> o Gateway
lab-istio  A      172.231.211.233       o endereco do Gateway
✓ HTTP em 172.231.211.233: 200 -- quem respondeu foi o Gateway lab
----

Cada linha é um salto da resposta: o nome aponta para o `Service` do Gateway, e
o `Service` tem um endereço. A última linha prova que o endereço é o certo -- a
chamada HTTP foi feita **nele**, com o nome da API.

O cliente é um pod com um resolvedor de trinta linhas em Python.

== 4. Geografia e peso: multicluster num cluster só

Esta é a parte que a `DNSPolicy` tem e nenhuma outra policy tem. Acrescentando
três campos:

[source,yaml]
----
spec:
  loadBalancing:
    defaultGeo: true
    geo: GEO-NA
    weight: 120
----

ifdef::foco_rhcl[]
O terceiro arquivo é a mesma policy com esses três campos. Aplique, espere, e
leia os registros e a resolução de novo:

[source,bash,role="execute"]
----
oc apply -f passos/dns/03-geografia-e-peso.yaml
sleep 20
bash scripts/dns-nome.sh registros
bash scripts/dns-nome.sh resolve
----

endif::[]
a estrutura muda inteira:

[source,text]
----
zona dns-lab.rhcl.internal
api
└─ CNAME klb.api                       ponto de decisao, por regiao
   ├─ geo GEO-NA -> geo-na.klb.api     o ramo da regiao
   │  └─ peso 120 -> lab-istio (svc)   o Gateway deste cluster
   └─ geo *      -> geo-na.klb.api     defaultGeo: as outras, mesmo ramo

pergunta: api  (zona dns-lab.rhcl.internal, ao CoreDNS do laboratorio)
api             CNAME  klb.api               o nome publico
klb.api         CNAME  geo-na.klb.api        decisao: o ramo da sua regiao
geo-na.klb.api  CNAME  lab-istio (svc)       o destino (com peso)
lab-istio       A      172.231.211.233       o endereco do Gateway
✓ HTTP em 172.231.211.233: 200 -- quem respondeu foi o Gateway lab
----

A árvore é o que foi publicado; a pergunta é o caminho que **uma** consulta
percorreu nela -- um salto a mais em cada nível. Leia a árvore de cima para
baixo:

* o nome público vira um **CNAME para um ponto de decisão**, o `klb.`;
* do `klb.` sai **um ramo por geografia** -- e um ramo `*`, que é o
  `defaultGeo`: quem não casa com nenhuma região cai nele;
* de cada ramo geográfico saem os **destinos, com peso**.

Com dois clusters, cada um publica o próprio ramo **na mesma zona**. Quem
resolve o nome recebe o destino da sua região; dentro da região, o peso
distribui. Não há balanceador no meio, e nenhum dos clusters sabe do outro --
os dois só escrevem seus registros.

É a mesma API, com os mesmos três campos, tanto aqui quanto num cenário real
com Route53 ou Azure DNS. Muda o `Secret` do provedor.

== 5. O nome tem dono

ifdef::foco_rhcl[]
Apague a policy -- só ela, o Gateway e o CoreDNS ficam -- e pergunte o nome de
novo:

[source,bash,role="execute"]
----
oc delete dnspolicy lab -n dns-lab
oc wait --for=delete dnsrecords.kuadrant.io --all -n dns-lab --timeout=90s
bash scripts/dns-nome.sh registros
bash scripts/dns-nome.sh resolve
----

endif::[]
[source,text]
----
(nenhum DNSRecord: sem DNSPolicy, ninguem cria o nome)
pergunta: api  (zona dns-lab.rhcl.internal, ao CoreDNS do laboratorio)
NXDOMAIN -- ninguem criou o nome "api" nesta zona
----

Ninguém apagou registro à mão. A policy saiu, os dois `DNSRecord` saíram com
ela -- o dono deles era a policy -- e o nome deixou de existir em segundos
(medido: cerca de 3 s). É o outro lado da seção 2: quem publica o nome é a
declaração, e quem o retira também. Não sobra registro órfão apontando para um
Gateway que já não atende.

ifdef::foco_rhcl[]
== Limpando

[source,bash,role="execute"]
----
bash scripts/dns-nome.sh limpa
----

A limpeza é um script, e não um `oc delete project`, por um motivo medido: os
registros precisam ser finalizados **antes** de o projeto sumir, senão ele fica
preso em `Terminating`. O script apaga a policy (se ainda houver), espera os
registros saírem, e só então remove o projeto.

endif::[]
== A parte honesta

[cols="1,3",options="header"]
|===
| ponto | o que vale saber

| o provedor `coredns`
| serve para DNS **interno** ou para quem opera o próprio servidor autoritativo.
  Para publicar na internet, o provedor é `aws`, `azure` ou `google`, com
  credencial e zona hospedada

| a imagem do CoreDNS
| vem do upstream do Kuadrant. Num ambiente de cliente, vale espelhá-la para o
  registro da casa e fixá-la por digest

| o endereço publicado
| é o que está no `status` do `Gateway`. Aqui é um `Service` interno, porque o
  cluster não tem LoadBalancer -- para DNS interno isso é o comportamento
  certo, e não um remendo

| geografia de mentira
| `GEO-NA` é só um rótulo. Quem resolve geografia de verdade é o provedor: os
  valores aceitos saem da documentação de cada um
|===

== O que isso prova

O nome de uma API é infraestrutura, e quase sempre mora fora do alcance de quem
publica a API -- vira chamado, planilha e espera.

A `DNSPolicy` o traz para o mesmo lugar das outras decisões: declarado ao lado
do `Gateway`, com status, com dono, e desfeito quando a policy sai. E, com
`loadBalancing`, a mesma declaração passa a responder uma pergunta que nenhuma
outra camada deste workshop responde: **qual cluster atende cada região**.

TIP: Se o exercício for interrompido, `bash scripts/dns-nome.sh limpa` remove o
namespace e os objetos de RBAC que ele cria.
