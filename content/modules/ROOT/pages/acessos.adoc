== As três chaves

Cada uma representa um cliente num plano comercial diferente. É a diferença
entre elas que o {m1} explora:

[cols="1,1,2",options="header"]
|===
| plano | para que serve | chave

| gratuito
| o limite mais apertado, e o que estoura primeiro
| `{api_key_free}`

| intermediário
| o meio-termo
| `{api_key_silver}`

| completo
| o que passa quando os outros já foram recusados
| `{api_key_gold}`
|===

Para chamar a API com uma delas, a chave vai na própria URL:

[source,bash,role="execute",subs="attributes+"]
----
curl -sk "https://{api_host}/travels?APIKEY={api_key_gold}" | head -c 300
----

[NOTE]
====
Chave em URL é o mais fácil de demonstrar, e **não** é o que se usa em
produção -- query string entra em log de acesso. O {m1} mostra que o
mesmo mecanismo aceita cabeçalho.
====

=== O seu repositório e o roteiro

Os dois ficam no GitLab deste ambiente. Na tela de login, clique em **Entrar
com o usuario do console** e use o mesmo usuário e a mesma senha do Console do
OpenShift -- não há conta separada.

* **O seu repositório** é a cópia que está no terminal do guia, em
  `/home/lab-user/rhcl-connectivity-demo`: policies, overlays e os scripts que
  as partes mandam rodar, com os namespaces e hostnames do seu ambiente. Pode
  editar e criar branch à vontade; nada dali é aplicado ao cluster sozinho.

`git commit` e `git push` funcionam dali, sem digitar credencial:

== As versões deste ambiente

"Em que versão você testou isso?" é a primeira pergunta de quem vai reproduzir
o workshop, e a segunda de quem abre um chamado. A resposta sai do cluster, não
de uma tabela:

[source,bash,role="execute"]
----
bash scripts/versoes.sh
----

Para colar num chamado ou num relatório, em markdown:

[source,bash,role="execute"]
----
bash scripts/versoes.sh --md
----

[NOTE]
====
A versão do **operador** não é a do que está servindo. O operador do
Connectivity Link diz `1.4.3`, mas quem decide cada requisição são o Authorino,
o Limitador e o _shim_ no proxy -- por isso a tabela separa as duas colunas.
====

== O terminal

O painel à direita já está autenticado no cluster. Não há login a fazer, e
não há senha a digitar. Confira:

[source,bash,role="execute"]
----
oc whoami && oc get httproute -A
----

A resposta do `oc whoami` é uma identidade de serviço
(`system:serviceaccount:...`), e não o seu usuário. É de propósito: o terminal
trabalha *por* você sem guardar a sua senha, e é essa identidade que tem as
permissões que os comandos do workshop usam. Não a troque.

ifeval::["{senha_console}" != ""]
.Quer ver a sua identidade pessoal no terminal?
[%collapsible]
====
Entre num arquivo de sessão *à parte*, que não mexe na sessão do terminal:

[source,bash,role="execute"]
----
KUBECONFIG=/tmp/eu.kubeconfig oc login -u {usuario_console} -p '{senha_console}' \
  --server=https://kubernetes.default.svc \
  --certificate-authority=/var/run/secrets/kubernetes.io/serviceaccount/ca.crt
KUBECONFIG=/tmp/eu.kubeconfig oc whoami
----

O segundo comando responde com o seu usuário. Repare no `KUBECONFIG=` na
frente dos dois: sem ele, o `oc login` substituiria a sessão do terminal, e os
comandos dos módulos passariam a falhar por falta de permissão -- o seu
usuário enxerga só o seu ambiente, e os scripts precisam ler também a
plataforma.
====
endif::[]

Os comandos dos módulos são executados a partir do diretório do workshop, que
já está no lugar certo quando o terminal abre.

== Se alguma coisa não responder

O ambiente é criado do zero para você, e uma peça ou outra pode demorar mais
que as demais. Antes de investigar, peça o veredito:

[source,bash,role="execute"]
----
bash scripts/demo.sh check
----

Ele confere a cadeia inteira e diz, em uma linha, se o workshop pode começar.
Avisos não impedem -- falhas, sim, e o texto diz qual módulo cada uma afeta.

Se a resposta for `bash: scripts/demo.sh: No such file or directory`, o
terminal saiu do diretório do workshop. Volte com:

[source,bash,role="execute"]
----
cd /home/lab-user/rhcl-connectivity-demo
----
