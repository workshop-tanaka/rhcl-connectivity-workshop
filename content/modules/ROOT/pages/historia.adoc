Neste workshop você acompanha a **Rota Viagens**, uma empresa fictícia de
serviços de viagem que está modernizando a própria infraestrutura -- e que,
no meio dessa mudança, descobriu que o produto mais valioso dela não é o site.

É a API.

== A aplicação

Os serviços já foram para o OpenShift. A aplicação não foi escrita para este
workshop: é o demo *Travels* do projeto Kiali
(https://kiali.io/docs/tutorials/travels/[tutorial do Kiali^]), e foi escolhida
por um motivo específico: **ela não tem uma linha de código sobre
autenticação, cotas ou identidade**. O binário é o mesmo de antes de existir
qualquer policy, e tudo que o workshop faz acontece *ao redor* dela.

== A API que você vai chamar

Um `HTTPRoute` publica o `travels` em `\https://{api_host}`. Dois caminhos
interessam ao workshop:

[cols="1,3",options="header"]
|===
| caminho | o que responde

| `GET /travels`
| **45 destinos**, direto do banco: `[{"city": "Amsterdam", ...}, ...]`. É a
  chamada mais usada no guia, porque é barata e fácil de conferir -- se vierem
  45 itens, a cadeia inteira funcionou

| `GET /travels/<cidade>`
| o **fan-out**: o `travels` chama os outros serviços e junta `flights`,
  `hotels` e `cars` numa resposta só. É este caminho que faz a aplicação ser
  mais que um serviço: uma chamada externa vira várias internas
ifndef::foco_rhcl[]
  -- e é por isso que o {m3} consegue mostrar um trace com vários saltos, e o
  {m2} tem o que proteger
endif::[]
ifdef::foco_rhcl[]
  -- e é por isso que uma recusa pode nascer em mais de um lugar, o assunto da
  fase de operação
endif::[]
|===

[NOTE]
====
**Abrir esse endereço no navegador dá tela em branco, e é o esperado**: sem
chave, a borda responde `401`, antes de olhar para onde a chamada vai. E a API
**não** expõe `/flights` nem `/hotels` na borda: com uma chave válida,
`\https://{api_host}/flights/Amsterdam` responde `404` -- é desenho, não falta.
====

== O que mudou no negócio

A Rota Viagens passou a vender acesso à própria API. Três parceiros já
assinaram, cada um num plano, e cada um tem o **próprio portal** -- uma
aplicação de terceiro, que consome a API como qualquer cliente externo faria:

[cols="1,3,1",options="header"]
|===
| plano | o que o contrato promete | portal

| gratuito | poucas chamadas, para quem está avaliando | Azul
| intermediário | volume moderado, para parceiros pequenos | Verde
| completo | o volume que os grandes parceiros exigem | Vermelho
|===

Os três portais rodam **a mesma aplicação**, com a mesma imagem. A única
diferença entre eles é a chave de API que cada um carrega. Os endereços, e as
três chaves, estão em xref:acessos.adoc[Seus acessos].

O contrato existe. **A plataforma não sabe disso.**

== Os quatro problemas que a equipe tem agora

Todos eles são consequência da mesma coisa: o que foi combinado no papel
nunca virou configuração.

**3. Quando um parceiro reclama, ninguém sabe onde parou.** *"Não consigo

Os quatro módulos resolvem os quatro problemas, nessa ordem -- o
xref:index.adoc[Sobre este workshop] traz a tabela com o que cada um entrega e
quanto tempo leva. O caminho curto: o **Módulo 1** resolve os problemas 1, 2 e
4 sozinho. Os outros tratam do que a borda não alcança.
endif::[]

== A tese que o workshop defende

Tudo que você vai fazer acontece **ao redor** da aplicação: o binário do
`travels` é o mesmo do primeiro ao último exercício. Se ao final a API estiver
fechada, vendida em planos e observada sem a aplicação ter mudado, a conclusão
se impõe sozinha: **o Connectivity Link não é um gateway com recursos extras.
É onde a API vira produto.**
