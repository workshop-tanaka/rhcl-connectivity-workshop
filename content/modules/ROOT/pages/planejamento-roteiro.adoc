= {p-roteiro}O roteiro: do piloto à produção
:navtitle: {p-roteiro}O roteiro: do piloto à produção

**Exercício · ~10 min · escreve no seu repositório e abre o merge request**

**Momento do projeto:** o kickoff · **Quem faz:** o time do projeto inteiro; o perfil Dev empurra, o perfil Infra aceita

[NOTE.antes]
====
**Antes:** as seis partes anteriores: o `plano.md` só ordena no tempo o que
elas decidiram.
====

Tudo o que a fase escreveu até aqui é o quê e o porquê. Esta parte é o
quando: seis marcos, do primeiro Gateway ao legado desligado, cada um com as
decisões que ele exige (das partes {p-fixas}e {p-parceiro-dec}desta fase), o critério
de pronto -- observável, como o do piloto -- e o risco que o marco carrega. No
fim, a pasta `planejamento/` inteira vai por merge request, como tudo desde a
fase 5.

== A migração do que existe

O cliente que decidiu raramente começa do zero; a Trajeto tem seis `Route` e
um gateway legado. A xref:leitura-ingresso.adoc[leitura sobre Route, Ingress e Gateway API]
mostra as três gerações convivendo no mesmo cluster; o plano transforma isso
em três passos, API por API:

. **Convivência.** A API nova nasce no Gateway, com nome novo, fechada e com
  plano; a antiga fica como está. Nenhum consumidor é obrigado a mudar no
  mesmo dia. Medido neste workshop: é o que o cluster do laboratório faz hoje.
. **Troca, consumidor a consumidor.** Cada consumidor passa a chamar o nome
  novo com a credencial nova; o painel por parceiro (parte {p-negocio}) diz
  quem já mudou e quem não. Para parceiros que **não podem** mudar de
  endereço, a alternativa é a rota nova assumir o **mesmo hostname** da
  antiga -- e isso **não foi medido neste workshop**: o corte no instante da
  troca, o DNS e o certificado que o parceiro já conhece precisam ser
  medidos em homologação antes de virar promessa.
. **Desligar.** O caminho antigo sai quando o painel mostrar zero chamadas por
  um período que produto define (a Trajeto: 30 dias), e não quando o
  cronograma mandar. É a mesma regra que a parte {p-versoes}usa para a v1.

A ordem das APIs da Trajeto, pelo critério de "quem tem menos consumidores a
mover primeiro": `tarifas` (piloto) → `relatorios` (M3) → as quatro `Route`
restantes → `busca-hoteis` e `busca-voos` (os 8 parceiros do legado, um a um)
→ o gateway legado desligado.

... planejamento: roteiro do piloto a producao

== Passo 2 -- abra o merge request

O mesmo caminho da parte xref:esteira-mr.adoc[{p-mr}Mudança por merge request]:
o push abre o merge request, e quem aceita é outra pessoa.

[source,bash,role="execute perfil-dev"]
----
git push -f -u -o merge_request.create -o merge_request.title='planejamento: o plano do kickoff' origin planejamento 2>&1 | grep -E 'merge_requests|new branch'
----

[source,text]
----
remote:   https://.../workshop/participantes/.../ambiente/-/merge_requests/4
 * [new branch]      planejamento -> planejamento
----

[NOTE]
====
**A conferência da fase 5 foi ampliada para esta pasta.** O pipeline que
recusa merge request mexendo fora de `esteira/` aceita também `planejamento/`
(e só ela): a conferência *Pipelines as Code CI / confere* fica verde porque
nenhum arquivo está fora das duas pastas. Um merge request que mexesse num
arquivo da raiz continuaria recusado, pela regra da parte {p-confere}A esteira confere antes.
====

ifeval::["{repo_no_ambiente}" != ""]
**Na console web:** {repo_no_ambiente}/-/merge_requests[os merge requests do seu projeto^]
(abre em aba nova). Na aba **Changes** estão os seis arquivos da pasta -- é
isso que quem aprova lê.
endif::[]

[IMPORTANT]
.Perfil Infra -- no GitLab, como `{usuario_console}`
====
Quem aceita é o **perfil Infra**, *Maintainer* do projeto. Abra o merge
request, leia os seis arquivos na aba **Changes**, espere a conferência
**Pipelines as Code CI / confere** ficar verde e clique em **Merge**. Nada
chega ao cluster com isso: o Argo CD lê só a pasta `esteira/`. O que o merge
dá à pasta `planejamento/` é autor, revisor e data -- e um lugar para o
próximo merge request mudar um número.
====

== Passo 3 -- confira o que ficou

[source,bash,role="execute perfil-dev"]
----
git checkout -q main && git pull -q && ls planejamento && git log --oneline -1 -- planejamento
----

[source,text]
----
decisoes.md  levantamento.md  papeis.md  piloto.md  plano.md  sizing.md
... Merge branch 'planejamento' into 'main'
----

**O que isso diz:** o plano está no `main` do seu repositório, com o merge de
quem o aceitou. O ambiente é efêmero (xref:99-encerramento.adoc[Encerramento],
"Leve o seu trabalho"): baixe o repositório antes de devolvê-lo -- a pasta
`planejamento/` sai junto com a `esteira/`.

== O que isso prova

**O plano tem o mesmo tratamento que a configuração.** Seis arquivos, cada
decisão com dono, data e o sinal que manda revê-la, cada número com a
premissa ao lado -- e cada mudança futura por merge request, com quem a
aceitou. O que o time leva para o kickoff não é um "entendi": é uma pasta.

E o que o plano **não** tem, de propósito: nenhum número que o workshop não
mediu virou promessa. O que ficou como "não medido" está na última tabela do
`plano.md`, com o marco antes do qual precisa ser medido -- no seu ambiente,
com os seus números. O time de Serviços da Red Hat é o apoio para essa parte.
