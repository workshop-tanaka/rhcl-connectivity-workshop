**Para quem:** Arquitetura e Segurança -- a integração B2B em que o
parceiro não quer chave de API.

[NOTE.antes]
====
**Antes:** a parte xref:m1-07-identidade.adoc[{p-identidade}], que compara chave e
token. Esta página traz a terceira credencial: o certificado de cliente.
====

*"E se o parceiro quiser se identificar por certificado, e não por chave?"* É
a pergunta de toda conversa B2B. A resposta honesta tem três partes, e só a
terceira funciona.

[NOTE]
.Novo na 1.4
====
A autenticação por certificado X.509 na `AuthPolicy` é novidade da 1.4
(https://docs.redhat.com/en/documentation/red_hat_connectivity_link/1.4/html/release_notes[notas de lançamento^]). O que esta página mede
vale para o Gateway nativo desta sessão; a leitura {p-previas}reúne o que mudou
de versão.
====

== Terminal

[source,bash,role="execute"]
----
bash scripts/parceiro-certificado.sh
----

Leva cerca de dois minutos, e remove tudo no fim.

[IMPORTANT]
====
**Por que não no Gateway da API.** Exigir certificado no `prod-web` recusaria
todos os clientes que você usou até aqui. O exercício sobe um Gateway **só
dele**, num namespace próprio, com uma CA de parceiros própria emitida pelo
cert-manager.

O "parceiro" é um pod no mesmo namespace, com os certificados montados. As
chaves privadas nunca saem do cluster.
====

== 1. O Gateway exige certificado

O listener do Gateway fica em modo `MUTUAL`:

[source,yaml]
----
tls:
  mode: Terminate
  certificateRefs: [{name: servidor, kind: Secret}]
  options: {gateway.istio.io/tls-terminate-mode: MUTUAL}
----

.Mais detalhes: o que cada campo do listener faz
[%collapsible]
====
[source,yaml]
----
listeners:
- name: https
  protocol: HTTPS                                            # <1>
  tls:
    mode: Terminate                                          # <2>
    certificateRefs: [{name: servidor, kind: Secret}]        # <3>
    options: {gateway.istio.io/tls-terminate-mode: MUTUAL}   # <4>
----
<1> **TLS no Gateway.** Com `HTTPS`, o bloco `tls` é obrigatório.
<2> **Quem termina o TLS.** `Terminate` é o Gateway, que então enxerga a
    requisição; `Passthrough` repassa os bytes cifrados ao backend, e aí
    nenhuma policy de borda lê nada.
<3> **O certificado do servidor**: um `Secret` do tipo `kubernetes.io/tls`.
    Aqui quem o emite é o cert-manager, e o mesmo `Secret` carrega a CA
    (`ca.crt`) contra a qual o cliente é validado.
<4> **Exigir certificado do cliente.** `options` é o campo da Gateway API
    para o que é do provedor; este valor é o do Istio e pede TLS mútuo. É
    o que produz o `exit=56` sem certificado -- e o que deixa o intruso
    entrar, porque validar a CA não é reconhecer o parceiro.
====

A CA de parceiros emitiu dois certificados de cliente: `parceiro-gold` e
`intruso`.

[source,text]
----
2. So o listener em MUTUAL, sem AuthPolicy
  sem certificado          http=000 exit=56
  parceiro-gold            http=200 exit=0
  intruso (mesma CA)       http=200 exit=0
----

Sem certificado, o handshake TLS nem termina (`exit=56`). Mas **o intruso
entra**. O listener prova que o certificado veio da CA certa, e não **quem**
é o parceiro. Uma CA que emite para dez parceiros abre a porta para os dez.

== 2. A AuthPolicy com `x509` não enxerga o certificado

O Connectivity Link tem uma forma de autenticação feita para isso: `x509`, que
valida o certificado do cliente contra uma CA guardada num Secret.

[source,text]
----
3. A AuthPolicy com x509 -- o caminho da documentacao
  parceiro-gold            http=401  x-ext-auth-reason: client certificate is missing
----

O Envoy **validou** o certificado no handshake, e mesmo assim o Authorino diz
que ele não veio.

O motivo é o caminho da chamada. O Envoy do Gateway pergunta ao Authorino por
meio do filtro do Connectivity Link no Gateway (o wasm-shim), e esse filtro
não repassa o certificado do
cliente nessa pergunta. Nesta versão, com `x509`, **ninguém entra**.

WARNING: Isto foi medido no RHCL 1.4. Não tome como definitivo em outra versão:
refaça o exercício antes de decidir.

== 3. O contorno: o Gateway escreve o certificado num cabeçalho

Duas peças:

. O Gateway passa a escrever o certificado que ele validou no cabeçalho
  `x-forwarded-client-cert` (XFCC). O modo `SANITIZE_SET` **apaga** o XFCC que
  vier do cliente e escreve o verdadeiro.
. A AuthPolicy decide pelo `CN` escrito nesse cabeçalho.

[source,yaml]
----
# no Gateway
spec:
  infrastructure:
    annotations:
      proxy.istio.io/config: '{"gatewayTopology":{"forwardClientCertDetails":"SANITIZE_SET"}}'
---
# na AuthPolicy
rules:
  authentication:
    certificado-validado-no-gateway:
      plain: {selector: request.headers.x-forwarded-client-cert}
  authorization:
    so-parceiros-conhecidos:
      patternMatching:
        patterns:
        - selector: request.headers.x-forwarded-client-cert
          operator: matches
          value: 'Subject="CN=parceiro-(gold|silver|free)"'
----

.Mais detalhes: o que cada campo do contorno faz
[%collapsible]
====
[source,yaml]
----
# no Gateway
spec:
  infrastructure:
    annotations:
      proxy.istio.io/config: '{"gatewayTopology":{"forwardClientCertDetails":"SANITIZE_SET"}}'   # <1>
---
# na AuthPolicy
rules:
  authentication:
    certificado-validado-no-gateway:
      plain: {selector: request.headers.x-forwarded-client-cert}   # <2>
  authorization:
    so-parceiros-conhecidos:
      patternMatching:
        patterns:
        - selector: request.headers.x-forwarded-client-cert       # <3>
          operator: matches
          value: 'Subject="CN=parceiro-(gold|silver|free)"'
----
<1> **Configuração do proxy**, passada ao Gateway por `infrastructure.annotations`
    (o campo da Gateway API para anotações do que o provedor cria).
    `SANITIZE_SET` apaga o `x-forwarded-client-cert` que veio de fora e
    escreve o do certificado validado no handshake.
<2> **Identidade vinda de um atributo.** `plain` não autentica nada: toma o
    valor apontado por `selector` como identidade. Só é seguro porque o
    passo 1 garante que esse cabeçalho é do Gateway.
<3> **A outra forma de padrão.** Em vez de um `predicate` em CEL (como nas
    partes {p-contextos} e {p-listas}), um `selector`, um `operator` e um
    `value`: com `matches`, o valor é uma expressão regular sobre o
    `Subject` do certificado.
====

[source,text]
----
4. O contorno: o Gateway escreve o certificado num cabecalho
  sem certificado                http=000 exit=56
  parceiro-gold                  http=200 exit=0
  intruso (mesma CA)             http=403  x-ext-auth-reason: Unauthorized
  intruso forjando o cabecalho   http=403  x-ext-auth-reason: Unauthorized
----

A última linha é a que importa. O intruso manda o cabeçalho escrito à mão,
dizendo ser `parceiro-gold`, e leva `403`. O Gateway substituiu o cabeçalho
pelo certificado que o intruso de fato apresentou.

[IMPORTANT]
====
**Sem o `SANITIZE_SET`, o contorno é uma porta aberta.** O XFCC vira só mais
um cabeçalho, que qualquer cliente preenche como quiser. As duas peças só
funcionam juntas.
====

== O que isso prova

Certificado de cliente responde duas perguntas diferentes, e cada uma tem um
dono:

* **O certificado é legítimo?** Quem responde é o listener do Gateway, no
  handshake.
* **Este parceiro pode entrar?** Quem responde é a AuthPolicy, com a regra
  declarada.

O caminho nativo para a segunda pergunta não funciona nesta versão, e o
contorno funciona **porque** a primeira resposta chega à segunda por um canal
que o cliente não controla. Se não fosse assim, a AuthPolicy estaria julgando
o que o cliente disse de si mesmo.

.Outro caso de uso: e se o certificado do parceiro vier de outra CA?
[%collapsible]
====
Hoje o listener valida o cliente contra a CA que está no `ca.crt` do
`Secret` do próprio servidor, e o laboratório emite os certificados dos
parceiros nessa CA. Um parceiro que traz a própria CA precisa que **ela**
esteja entre as confiadas pelo listener -- um `Secret` cujo `ca.crt` reúna
as CAs aceitas --, e a regra do passo 3 continua decidindo pelo `Subject`.
Não medido neste ambiente: antes de prometer isso a um parceiro, refaça o
exercício com a CA dele.
====
