= A aplicação e as APIs
:navtitle: A aplicação e as APIs

Antes de governar uma API, vale saber qual API é. Esta página descreve o que
está rodando no seu cluster -- e o que **não** está, que também importa.

== O que é a travel-agency

Uma agência de viagens de exemplo, com sete serviços em `travel-agency`. Ela
foi escolhida por um motivo específico: **ela não tem uma linha de código
sobre autenticação, cotas ou identidade**. O binário é o mesmo de antes de
existir qualquer policy.

Tudo que o workshop faz acontece *ao redor* dela. É isso que permite dizer,
ao fim, que a plataforma fez o trabalho -- e não a aplicação.

=== Os sete serviços

[cols="1,2,1",options="header"]
|===
| serviço | o que faz | exposto?

| `travels`
| a porta de entrada da aplicação. Recebe a chamada e chama os outros
| **sim**, via `HTTPRoute`

| `flights`
| companhias aéreas e preços
| não, só interno

| `hotels`
| hospedagem
| não

| `cars`
| locação de veículos
| não

| `insurances`
| seguro viagem
| não

| `discounts`
| descontos aplicáveis -- e o único com **duas versões** (`v1` e `v2`) no ar
| não

| `mysqldb`
| o banco com os destinos
| não
|===

Só o `travels` tem rota externa. Os outros seis existem **atrás** dele, e é
essa assimetria que o Módulo 2 explora: proteger a entrada não diz nada sobre
o que acontece depois dela.

=== O `discounts` tem duas versões de propósito

`discounts-v1` e `discounts-v2` rodam ao mesmo tempo. É esse par que torna
possível a parte 2.2, onde uma fração do tráfego vai para a versão nova sem
ninguém trocar imagem de Deployment.

== A API que você vai chamar

Um `HTTPRoute` publica o `travels` em:

[cols="1,3"]
|===
| endereço | `\https://{api_host}`
|===

[NOTE]
====
**Abrir esse endereço no navegador responde `401`, e é o esperado.** A API
nasce fechada: sem uma chave de API na requisição, a borda nega antes de a
aplicação ser consultada -- e o navegador não manda chave nenhuma. Não é o
ambiente fora do ar; é a primeira policy do workshop funcionando. A
xref:m1-01-fechada.adoc[parte 1.1] começa exatamente por esse `401`.
====

Dois caminhos interessam ao workshop:

=== `GET /travels` -- a lista de destinos

Responde **45 destinos**, direto do banco:

[source,json]
----
[{"city": "Amsterdam", "lat": "52.3500", "lng": "4.9166"}, ...]
----

É a chamada mais usada nos módulos, porque é barata e a resposta é fácil de
conferir: se vierem 45 itens, a cadeia inteira funcionou.

=== `GET /travels/<cidade>` -- o fan-out

Aqui o `travels` chama os outros serviços e junta tudo numa resposta só:

[source,json]
----
{
  "city": "Amsterdam",
  "status": "Valid",
  "flights": [{"airline": "KLM", "price": ...}, ...],
  "hotels":  [...],
  "cars":    [...]
}
----

**É este caminho que faz a aplicação ser mais que um serviço.** Uma chamada
externa vira várias internas -- e é por isso que o Módulo 3 consegue mostrar
um trace com vários saltos, e o Módulo 2 tem o que proteger.

[NOTE]
====
A API **não** expõe `/flights` nem `/hotels` na borda: esses serviços só são
alcançáveis por dentro. Chamar `\https://{api_host}/flights/Amsterdam` com uma
chave válida responde `404` -- e isso é desenho, não falta. Sem chave a
resposta é `401`, como em qualquer caminho: a borda confere quem chama antes
de olhar para onde.
====

== Os três portais de parceiro

A Rota Viagens vende acesso à API. Três parceiros já assinaram, e cada um tem
o **próprio portal** -- uma aplicação de terceiro, que não pertence à Rota
Viagens e que consome a API como qualquer cliente externo faria.

[cols="1,1,2",options="header"]
|===
| portal | plano | endereço

| Azul | gratuito | {portal_free_url}[abrir^]
| Verde | intermediário | {portal_silver_url}[abrir^]
| Vermelho | completo | {portal_gold_url}[abrir^]
|===

Os três rodam **a mesma aplicação**, com a mesma imagem. A única diferença
entre eles é a chave de API que cada um carrega -- e é essa diferença que os
Módulos 1 e 3 exploram.

.Mais detalhes: onde a chave do parceiro fica, e por que isso importa
[%collapsible]
====
O portal é Angular com renderização no servidor. O navegador chama
`/api/getcities` no **próprio servidor Node do portal**, e é esse servidor que
chama a API de viagens acrescentando a chave.

[source,text]
----
navegador  ->  servidor do portal  ->  API de viagens
                    (a chave entra aqui)
----

Duas consequências:

**A chave nunca chega ao navegador.** Ninguém a copia do DevTools. É como um
portal de parceiro real se comporta, e é o motivo de a chave ser uma
credencial de **sistema**, não de pessoa.

**Não há CORS envolvido.** O navegador só conversa com a origem do próprio
portal, então não existe chamada _cross-origin_. Uma página que chamasse a API
direto do navegador precisaria que a API autorizasse a origem -- e isso também
se resolve na borda, com dois cabeçalhos no `HTTPRoute`, sem tocar na
aplicação.
====

== O banco está no cluster -- por enquanto

O `mysqldb` que a aplicação usa roda em `travel-agency`, ao lado dos outros
serviços e dentro do Service Mesh. Os 45 destinos saem dele.

Em cliente real é comum que não seja assim -- *"esse banco não vai para o
Kubernetes"* -- e alcançá-lo de fora do cluster, sem VPN e sem expor nada, é
o assunto do xref:m4-00-intro.adoc[Módulo 4], que está a caminho.

== A segunda API: `echo-api`

Existe uma segunda aplicação no cluster, bem menor, chamada `echo-api`. Ela
devolve o que recebe, e serve para demonstrar autenticação por **identidade**
(OIDC) em vez de chave de API.

Você não precisa dela nos Módulos 1 e 2. Ela aparece como contraste quando o
assunto é *de onde vem a identidade de quem chama*.

== E as APIs que você mesmo vai criar

No Módulo 1 você publica uma API nova, do zero -- à mão, para sentir
o que falta. Essa API é sua, nasce
e morre dentro do módulo, e não toca em nada descrito nesta página.

== Confira você mesmo

[source,bash,role="execute"]
----
oc get deploy,svc -n travel-agency
----

[source,bash,role="execute",subs="attributes+"]
----
curl -sk "https://{api_host}/travels?APIKEY={api_key_gold}" | head -c 200; echo
----

O primeiro mostra os sete serviços; o segundo, os destinos que vieram do banco.
