== 1. O Connectivity Link e um provedor de Gateway

O Connectivity Link não cria Gateways: ele aplica policies sobre os que um
**provedor de Gateway API** cria. O requisito é esse provedor -- e há mais de
uma forma de atendê-lo.

ifndef::foco_rhcl[]
[NOTE]
====
**O Service Mesh não é requisito do Connectivity Link.** A partir do OpenShift
4.19 o Gateway API é nativo da plataforma, e dá para usar o Connectivity Link
sobre ele, sem instalar o Service Mesh.

Este ambiente usa o OpenShift Service Mesh 3 como provedor porque o workshop
vai além da borda. Duas coisas aqui dependem do Service Mesh propriamente
dito:

* o **{m2}** inteiro -- mTLS entre serviços, autorização leste-oeste,
  canário e circuit breaker são funções do Service Mesh, com sidecar nos pods
  da aplicação;
* o campo **`mtls.enable`** do passo 3, que põe o Authorino e o Limitador no
  Service Mesh.

Quem precisa só da borda -- autenticação, limites e planos, o que o {m1}
mostra -- pode ficar com o Gateway API nativo.
====

Aqui são duas instalações pelo OperatorHub:

[cols="1,2,2",options="header"]
|===
| operator | onde é instalado | o que entrega

| OpenShift Service Mesh 3
| `openshift-operators`
| o control plane do Istio e a classe de Gateway que o Connectivity Link usa

| Red Hat Connectivity Link
| `kuadrant-system`, com `OperatorGroup` próprio
| o operator do Kuadrant e, junto com ele, os do Authorino, do Limitador e
  de DNS
|===
endif::[]
ifdef::foco_rhcl[]
[IMPORTANT]
====
**O Service Mesh não é requisito do Connectivity Link, e este ambiente é a
prova.** A partir do OpenShift 4.19 o Gateway API é nativo da plataforma. Aqui
o Connectivity Link roda sobre ele, e não há Service Mesh instalado.

O que se perde sem o Service Mesh é o que é função dele: identidade e
autorização **entre** os serviços, divisão de tráfego entre versões, e o canal
cifrado entre o Gateway e os componentes do Connectivity Link (o campo
`mtls.enable` do passo 3). Nada do que esta sessão pratica depende disso.
====

Aqui é uma instalação só pelo OperatorHub:

[cols="1,2,2",options="header"]
|===
| operator | onde é instalado | o que entrega

| Red Hat Connectivity Link
| `kuadrant-system`, com `OperatorGroup` próprio
| o operator do Kuadrant e, junto com ele, os do Authorino, do Limitador e
  de DNS
|===

O provedor de Gateway não é um operator a mais: vem com o próprio OpenShift,
e o passo 2 mostra como ele é ligado.
endif::[]

A instalação do Connectivity Link é uma `Subscription`:

[source,yaml]
----
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: rhcl-operator
  namespace: kuadrant-system
spec:
  channel: stable
  name: rhcl-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Automatic
----

Um pedido, quatro operators. Veja o que ela trouxe:

[source,bash,role="execute"]
----
oc get csv -n kuadrant-system | grep -E 'rhcl|authorino|limitador|dns-operator'
----

[cols="1,3",options="header"]
|===
| componente | papel

| Kuadrant operator
| lê as policies que você declara e as traduz em configuração do Gateway

| Authorino
| decide **quem entra**: valida a chave ou o token de cada requisição

| Limitador
| decide **quanto passa**: conta as requisições contra o limite do plano

| DNS operator
| publica nomes em provedores de DNS, quando há `DNSPolicy`
|===

== 2. O provedor vem antes

Como o Connectivity Link governa Gateways que outro componente cria, o
provedor é configurado primeiro.

ifndef::foco_rhcl[]
Neste ambiente é o Service Mesh -- um CR
`Istio` e um `IstioCNI` -- e é dele que nasce a `GatewayClass` chamada
`istio`. Com o Gateway API nativo do OpenShift, a classe seria outra, e o
resto desta página valeria igual.

[source,bash,role="execute"]
----
oc get gatewayclass
oc get istio default -o jsonpath='{.spec.version}{"\n"}'
----
endif::[]
ifdef::foco_rhcl[]
Neste ambiente é o Gateway API nativo do OpenShift: o próprio cluster instala e
mantém um Istio só para atender Gateways, sem Service Mesh. A `GatewayClass` se
chama `istio`, e o controller dela é `openshift.io/gateway-controller/v1`. Com o
Service Mesh como provedor haveria um CR `Istio` e um `IstioCNI` no lugar, e o
resto desta página valeria igual.

[source,bash,role="execute"]
----
oc get gatewayclass
----

A classe `openshift-default`, que aparece ao lado, é a que faz o cluster
instalar esse Istio; nenhum Gateway do workshop a usa.
endif::[]

Sem essa classe, um `Gateway` declarado fica sem ninguém para atendê-lo.

== 3. Um objeto liga a plataforma

Com os operators de pé, nada acontece ainda. O que sobe o Authorino e o
Limitador é um único objeto, o CR `Kuadrant`:

[source,bash,role="execute"]
----
oc get kuadrant kuadrant -n kuadrant-system -o jsonpath='{.spec}{"\n"}'
----

Neste ambiente ele traz duas decisões:

[cols="1,3",options="header"]
|===
| campo | o que faz

ifndef::foco_rhcl[]
| `mtls.enable: true`
| põe o Authorino e o Limitador no Service Mesh, e o Gateway passa a falar
  com os dois por mTLS. A xref:m2-04-canal.adoc[parte {p-canal}] mede esse salto
endif::[]
ifdef::foco_rhcl[]
| `mtls.enable: false`
| o Gateway fala com o Authorino e o Limitador **sem** mTLS. Ligar esse campo
  pede o Service Mesh, que é quem dá identidade aos dois lados; sem ele, o
  canal fica protegido só pelas regras de rede do cluster
endif::[]

| `components.developerPortal.enabled: true`
| liga o portal do desenvolvedor: os tipos `APIProduct` e `APIKey` e as telas
  de produtos de API na console
|===

E os componentes que esse objeto fez nascer:

[source,bash,role="execute"]
----
oc get pods -n kuadrant-system
----

ifndef::foco_rhcl[]
[NOTE]
====
O `mtls.enable` é ligado **na criação** do ambiente, e não depois. Ligá-lo com
tráfego passando reinicia o Authorino e o Limitador; uma medição registrou
cerca de 8 segundos de `500` para todas as APIs. A falha foi fechada -- nenhuma
requisição sem chave passou -- mas é uma janela que não precisa existir.
====
endif::[]
ifdef::foco_rhcl[]
[NOTE]
====
**Aqui entraria o Service Mesh.** Com ele, o `mtls.enable` vira `true` e o salto
entre o Gateway e os componentes do Connectivity Link passa a ser cifrado e
autenticado. É uma decisão para tomar **na criação** do ambiente: ligá-lo com
tráfego passando reinicia o Authorino e o Limitador. A
xref:papel-ossm.adoc[leitura sobre o papel do Service Mesh] diz o que mais muda.
====
endif::[]

== 4. O Gateway, o certificado e a publicação

O `Gateway` é um objeto do Gateway API, da classe `istio`:

[source,bash,role="execute"]
----
oc get gateway prod-web -n ingress-gateway -o yaml
----

Três escolhas estão nele, e cada uma tem um motivo:

* **O listener é um curinga** (`*.apps...`), e não um hostname exato. É o que
  permite que mais de uma rota se anexe ao mesmo Gateway -- e são as policies
  de Gateway valendo para várias rotas que a
  xref:m1-03-precedencia.adoc[parte {p-precedencia}] usa para mostrar a precedência.
* **O TLS termina no Gateway**, com o certificado curinga que o cluster já
  tem. Os hostnames das APIs têm **um rótulo só** (`api-travels.apps...`)
  justamente para caberem nesse curinga.
* **Quem publica é uma `Route` do OpenShift em modo passthrough.** Não há
  balanceador externo dedicado ao Gateway neste ambiente; o router do
  OpenShift entrega os bytes sem abrir o TLS, e o Gateway termina a conexão.

[source,bash,role="execute"]
----
oc get route -n ingress-gateway
----

A xref:leitura-ingresso.adoc[leitura sobre Route, Ingress e Gateway API]
explica por que os três convivem.

== Três coisas que a instalação ensinou

Nenhuma delas dá erro na hora. Todas foram medidas neste material.

. **O operator do Kuadrant vem com 300 Mi de memória.** Com centenas de
  policies no cluster ele passa disso e reinicia -- e as policies criadas
  enquanto ele está fora não são aplicadas. Num ambiente grande, o limite é
  ampliado pela `Subscription`.
. **Um hostname de dois rótulos sai do curinga do cluster.** Emitir um
  certificado próprio para `api.travels.apps...` por DNS pode fazer o nome
  parar de resolver, com o certificado saindo como válido. Hostnames de um
  rótulo, sob o curinga que já existe, evitam o problema.
. **`Enforced=True` não é promessa de efeito.** O status diz que a policy foi
  aceita e programada. Se ela produz o efeito esperado, só o tráfego responde
  -- e é por isso que cada parte deste workshop mede em vez de confiar no
  status.
